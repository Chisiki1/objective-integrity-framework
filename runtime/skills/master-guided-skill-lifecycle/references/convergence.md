# Convergence at the next consumer

Apply at an actual decision-bearing result or recurrence, not every read or timer. The user's complete objective, mandatory conditions, independent review and action authority remain unchanged. Use the existing objective view, Project event, allocation/transition record and learning candidate; do not introduce another semantic store or approval phase.

## Make the unit advance the required result

Identify the next missing connection to the user's outcome: the real caller/input, decision, effect owner, retained state/recovery and result consumer, as applicable to this job. For research or documents this can be the source-to-conclusion or draft-to-delivery connection, not an invented runtime requirement. Preserve all other open outcomes.

Prefer bounded internal work whose result enters the full requested deliverable. Keep the whole source completion scope fixed while splitting construction; a bounded unit must not become an independent formal-acceptance cycle ahead of unfinished implementation/connections. Before designing another disconnected component, compare integrating existing pieces with independent preparation. Identify the concrete omission keeping the full result open. A design with an abstract required caller, writer, reader or recovery contract is not integration-ready. Partial artifacts retain their value, proof ceiling and integration owner, never overall completion. Apply [source-wide-execution.md](source-wide-execution.md) when this local-cycle recurrence is present: parent control and dispatch consume the same scope/phase decision, instead of another reminder.

Useful parallel components, safe diagnosis, finite tests, real-progress waits and external dependencies remain allowed. No fixed WIP limit, time quota, mandatory new agent or full-runtime prerequisite is introduced. A changed dependency invalidates only affected claims; a new candidate name alone does not justify repeating unchanged work.

## Change the entrypoint that permitted recurrence

After a failure uncovers a downstream state, inspect the same affected writer/reader/ownership/recovery relationships and independent safe downstream paths before the next dependent retry. Preserve the first fault and do not assume every later defect was introduced by the previous patch. Do not expand to unrelated whole-system re-audit.

For a known family, name the changed actual input, shared builder/consumer, retrieval route or dispatch instruction and the falsifiable next result. A new version number or repeated reminder with identical failing input is not a correction. For existing-file operations use paths returned by an exact inventory/manifest; absent or ambiguous members stay unresolved rather than being guessed. This does not prohibit authorized creation of a new file. Before a source transformation, use actual source bytes and validate intended changes together before publishing the candidate.

For stage allocation, build typed orchestration facts and use `allocation_io.py` to consume the same allocator's real decision and bound selection. Missing runtime facts remain unavailable. Do not translate a successful `SELECTED` into failure because the caller expected `RETAIN_CURRENT`; do not accept a held result or a selected configuration different from the one actually dispatched. Reuse is not a model identity or permission.

## Deliver learning to the next job

The next applicable job receives the concrete changed method or helper, its exact identity, allowed scope and real next-use condition. Required source/Skill reading and blind independence remain individual obligations. A parent reader's receipt does not certify a child's reading. Reuse only genuinely covered unchanged material under the applicable instructions; supplied excerpts are not complete reading of a required file. Do not add full-policy rereading merely because a new internal job was created, and do not remove reading that higher-priority instructions require.

Consume current controls and all applicable history through the existing source-bound index when useful. Keep raw history and every unresolved/contradictory/failure ID, but use a scoped current view for the present decision. Old task controls remain historical, not present authority. For the current ledger, outcome_updates[].evidence_refs merges with that outcome's prior references; submit only new references there. Top-level latest_progress is replaced, not cumulatively merged: include the evidence needed for the current decision and explicit journal/event or stable-index links for older dependencies. Do not blindly copy the entire growing evidence list, drop a needed current dependency, or rewrite another chat's ledger. The complete journal remains the history source.

At the next real use, record what the changed action did, whether the same error recurred, induced holds/rework and available elapsed/integration cost. Replay tests are preparation; actual use and independently observed outcome are separate. If ineffective, revise, merge, narrow or retire the method while preserving original knowledge. If next use is unavailable, retain the exact trigger without claiming benefit or inventing background execution. Existing-authority improvements proceed once eligible; only an actual condition amendment waits for its exact user approval.

## Compare structural alternatives when they can change the result

Autonomous improvement includes breakthrough candidates, not only local repairs. At actual stalled integration, recurrence, avoidable support cost, a successful reusable method or capability change, compare the current route with a smaller fix and, where promising, a different work unit, representation, execution entrypoint, ownership arrangement, or removal/consolidation. Identify which costly dependency or recurring manual choice would disappear or change, the real next consumer and the observable result that could refute the expected benefit. This is a source-preserving choice, not a requirement for a fixed number of ideas, a new framework, maximum novelty or a brainstorm on every prompt.

Use one already-needed work unit for a bounded trial when that can establish the relevant effect. Include setup, integration, false holds and maintenance; do not choose only easy peripheral completions or require future success before an authorized experiment. When external facts can discriminate the method choice, apply [external-calibration.md](external-calibration.md) at this same decision, not a new phase: challenge the uncertain work-method assumption, reconcile current host capabilities and credible counterevidence, and place the selected concrete change in the actual next input/request. Fresh applicable prior evidence or a justified no-change decision avoids redundant searches. Technical API research alone does not establish method effectiveness. The successful unit and an important source-bound uncertainty resolved may both be useful progress. Existing-authority changes proceed through current gates without another prompt; exact user-condition amendments and separate external permissions remain separate. Preserve original conditions, failures and recovery lineage. If the structural route does not repay its cost, revise, merge, narrow, retire or return to the simpler route.

For repeated internal assignment/handoff, the optional [work entrypoint](work-entrypoint.md) generates the actual bounded request from owner-supplied source, scope, input/method and consumer facts. The owner uses that exact request, consumes the real result and checks the deliverable connection. A prepared request is not dispatch; a returned hash is not semantic integration; a successful component is not the primary outcome. Source changes and uncertain effects must remain visible without erasing useful old results or stopping unrelated work. Reuse existing masters/ledger as authority and history, never introduce another independently editable completion truth.

## Return to the objective

Compare the last actual integrated advance with the current unchanged obligations and next safe route. If supporting work repeats while the relevant consumer remains unchanged, change the work shape, input or integration priority using existing controls. Explain the changed decision briefly and execute it. Do not replace the original objective with bookkeeping, a new verifier or an easy passing subset. No claimed benefit is based on record, Skill, tool or test counts alone.
