# Source-wide execution

Keep the original requested outcome and all required implementation/consumer connections in the existing work definition. Internal jobs can be small; the completion and formal-verification scope cannot become the child job. This route replaces local verify/fix cycles, not useful incremental construction.

The owner keeps one immutable scope reference and one current state reference. Reuse their exact bindings in parent control, transition admission and work_io v2. Progress/objective.txt points to them and names remaining implementation/connections; it does not duplicate their matrix. Updating the state preserves old referenced evidence and source lineage. Only the source-authorized owner changes scope, not a child result. A valid source amendment requires the existing ledger/condition route; this helper cannot authorize it.

## Select the next action

- BUILD: implement all requested parts and required connections. Before completion, formal checks redirect to remaining implementation. SCOPE_REVIEW is source/implementation reading, not acceptance. CONSTRUCTION_FEEDBACK includes cheap parse/type/compile and the smallest isolated semantic discriminator necessary to choose the next implementation. Bind its decision, return step, cost, effects and output ownership. It is not a new audit/correction cycle per diagnostic.
- SWEEP: freeze the whole candidate; owner and independent source-coverage readers check that it covers the original request. Collect current-stage safe checks and their findings without editing the candidate after the first failure. Safe independent partitions continue; unsafe dependencies remain explicitly blocked with first-fault evidence. Stages come from evidence availability, not convenient component boundaries. Later market/long-run evidence remains required but need not delay current known repairs.
- REPAIR: close and integrate the current-stage collection first. Repair mandatory findings by shared root cause and all affected consumers. Optional enhancements must not block completion or silently become new requirements. Recheck affected evidence and required whole acceptance; reuse unchanged valid evidence.
- ACCEPT: all mandatory implementation, findings and required checks, including later evidence, must close. A collected sweep, file hashes, a completion flag or component PASS never proves the user outcome.

Essential design errors, accepted-product regressions, uncontrolled/shared/unknown effects and external actions use the existing dependent diagnostic/authority route. Do not knowingly finish a wrong design, hide a regression as compiler feedback, or blanket-isolate safe reusable caches. The phase route does not replace those rules. Read-only diagnosis, research and documentation retain their own original outcomes and ordinary lightweight/direct routes; do not invent product phases.

## Exact data interface

`python -B scripts/work_phase.py --input <binding.json>` is read-only. Python callers use `evaluate(binding, objective_id=..., source_sha256=..., owner_chat_id=...)`. Result `admitted` is structural selection, not permission; inspect `next_actions`, `holds`, remaining implementation/checks, deferred evidence and findings. Invalid schema or stale identity raises ValueError/CLI failure. Do not silently continue an affected dispatch. Actual raw/partial/unknown results still need consumption even when the next action is held.

All refs below are `{path: <absolute plain regular file>, sha256: <actual full SHA256>}`. JSON rejects duplicate keys and non-finite constants. Freeze source bytes before deriving the scope. Hashes prove byte identity, not faithful interpretation. The evaluator returns its actual `input_refs`; work_io prohibits child outputs/results from aliasing those owner-controlled scope/state/proof files. Original-source coverage mistakes may be corrected by the owner with retained old identity, exact original clause and independent reconciliation; this is not permission to change user intent, drop requirements or relax conditions without required approval.

Binding fields: `state_ref`, `completion_scope_ref`, `action`, `item_ids`, `check_ids`, `finding_ids`, `feedback`. Actions are IMPLEMENT, SCOPE_REVIEW, CONSTRUCTION_FEEDBACK, FORMAL_CHECK, COLLECT_FINDINGS, REPAIR_FINDINGS and ACCEPT. Unused ID lists are empty, feedback is null except for construction feedback. Never pass a child-scope file as completion_scope_ref.

Scope `source-wide-scope-v1` fields: `schema`, `objective_id`, `owner_chat_id`, `source_ref`, `requirements`, `implementation_items`, `checks`, `coverage_review`. Requirements have `id`, `source_clause`, `description`. Implementation items have `id`, `requirement_ids`, `description` and include connections. Checks have `id`, `requirement_ids`, `stage`, `description`. Every requirement maps to implementation and verification. coverage_review has `owner_ref` and `independent_ref`; BUILD permits null while coverage is being read, later phases require both exact evidence refs. These are independent judgments to perform, not self-certifying flags.

State `source-wide-state-v1` fields: `schema`, `objective_id`, `owner_chat_id`, `source_sha256`, `completion_scope_ref`, `phase`, `current_stage`, `candidate_ref`, `implementation`, `checks`, `findings`, `findings_closed`. BUILD candidate_ref can be the actual baseline/planned manifest; later phases bind the frozen whole-candidate manifest. Item and check ID sets must exactly equal the complete scope, including later checks. current_stage must be a stage in that scope.

Implementation rows: `id`, status pending/complete, `evidence_ref` (null for pending). Check rows: `id`, status pending/pass/fail/blocked, `evidence_ref`, `reason`. A blocked check needs actual first-fault/dependency evidence and reason; it is not PASS. Later pending checks remain deferred. Findings: `id`, `check_id`, classification mandatory/optional, `basis`, `root_cause`, `consumer_item_ids`, status open/resolved, `evidence_ref`. Mandatory basis binds the original requirement, preservation or concrete safety/authority obligation; optional criteria do not become blockers.

For REPAIR_FINDINGS, finding_ids names every open mandatory finding in each selected cause group; item_ids includes that group's full consumer union. A finding cannot authorize editing while current-stage checks are pending or collection is unclosed. ACCEPT rejects missing/deferred/blocked required evidence. No fixed retry count is imposed.

Construction feedback has exactly `decision`, `return_step`, `cost_disposition`, `output_ownership` (nonempty text), `effect_class` (only owned-local admits), `effects_disposition` (known-bounded/unknown/harmful/external), and `applicability` (construction/accepted-product-regression/essential-design-failure). Only construction + known-bounded + owned-local is eligible. Other explicit values hold the dependent route without suppressing the recorded effect. See realistic fixtures in `scripts/test_work_phase.py`. Keep actual side effects and outcomes in the existing action record; no prose keyword heuristic or test name certifies safety.

## Connected consumers and adoption

Work_io `work-spec-v2` adds objective_id and work_phase to the existing spec. prepare/verify screen the actual dispatch; consume keeps raw results even if phase/source changed. Owner control v2 adds source_sha256, owner_chat_id and work_phase; ACT uses the selected action, CORRECT requires grouped repair. Transition admission v3 adds work_phase to v2 and checks it before lightweight routing; phase selection never overrides external authority or regression diagnosis.

Legacy inputs remain readable and explicitly report that source-wide selection was not evaluated. New implementation cannot claim adoption through a legacy receipt. The helper does not intercept host tools or force model compliance. Measure the actual next work and final integration/quality/rework/total cost in the next authorized consumer; test count, reduced check count and record volume are not benefit. Narrow or retire unnecessary overhead while preserving requirements.
