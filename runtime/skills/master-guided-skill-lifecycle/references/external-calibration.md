# External evidence that changes the next work

Use this inside the existing convergence/capability decision when a relevant outside fact could change the work method. No extra master, queue, ticket, approval phase, search quota or timer is introduced. Explicit user research requests and higher-priority browsing requirements still apply.

## Close the decision, not a research report

1. Name the uncertain assumption and the next action it affects. Distinguish a technical question (what an API means) from a method question (why this work unit or control should improve delivery). Source outcomes, conditions and first faults stay fixed.
2. Retrieve applicable current evidence from both masters before repeating research. Reuse genuinely read, fresh evidence with its limits. Search when the unresolved fact can discriminate unchanged reuse, a smaller repair, or a promising structural/removal alternative. A repeated method failure can trigger this without any version change; an ordinary finite success does not.
3. Prefer primary documentation, source code or original research. Search for credible contrary evidence and non-applicability, not only support for the favored method. Keep URL, publisher, retrieval date, relevant version, claim, applicability/limits and conflicts in the existing Project event/candidate. Do not upload private transcripts, sources, identifiers or secrets as queries. An unavailable or unhelpful source is not positive evidence.
4. Reconcile the external claim with this host, source and actual work. Another vendor's benchmark or API feature is not a Desktop capability or a local performance result. Compare setup, required reading, integration, false holds, induced rework and maintenance. Missing metrics remain unavailable.
5. Choose reuse, a bounded changed method, defer with a concrete return trigger, or reject. Stop gathering when the decision is sufficiently supported; unresolved information holds only the dependent claim/action. Put the selected concrete change and its evidence ceiling into the next actual action or existing work request. A link, reference-reading receipt or populated form is not that change.
6. Consume the real next result: did the chosen action enter its required consumer, resolve the named uncertainty, recur, cause a false hold or add waste? Use the existing lifecycle disposition. Within-authority eligible improvements proceed without another user prompt; exact condition/trust/external permissions remain separate. Do not claim broader improvement from this one episode.

For an internal handoff, reuse work_io's existing `instructions`, `inputs`, `methods` and `consumer` fields. For direct work, use the existing action record. Do not duplicate either with an independently editable decision database. A reviewer derives source criteria before receiving the favored hypothesis; calibrated evidence is then a challenge input, not an authority override.

## Current-feature and hook decisions

Identify the executable/host actually running the task, not merely the PATH alias or an API model catalog. Keep six boundaries separate: documented support; supplied configuration; exact trust; observed host event; actor identity; actual model/consumer use. Missing evidence for one boundary does not erase evidence for another. Preserve original tool feedback and pending side effects. Never manufacture Stop continuations, run network research inside a hook, bypass trust, or infer general coverage from one event.

For a repeated hook/capture inventory, `scripts/capability_snapshot.py --hooks <absolute hooks.json> [--journal <absolute journal.jsonl> --source-sha256 <exact digest>] [--runtime <absolute runtime.py>]` is an optional pure reader. It emits only metadata for supplied files. It does not invoke a ledger read/repair command, discover all configuration layers, evaluate trust, start a process, send anything, or validate journal history. Its journal parser is explicitly version-bounded to `user_prompt_source` metadata, not the unstable host transcript format. Missing, partial, oversized or changed inputs remain visible; capture counts cannot prove event delivery or semantic authority. Inspect every partition's status, not just the command exit. No output path is accepted: retain stdout only through the already authorized evidence route.

Use existing trusted recovery hooks where their actual boundary helps. Adopt a new hook only after its exact input/output, tool/actor coverage, representative normal/error paths, added value, trust and rollback close. An explicit-result route remains available for uncovered actions; a missing optional probe is not a task-wide stop.

## Dated evidence seeds, not evergreen host promises

Retrieved 2026-09-08 JST. Recheck only decision-sensitive drift or conflict; these notes are not version-independent guarantees.

- [OpenAI Hooks](https://learn.chatgpt.com/docs/hooks): local tool events and subagent lifecycle events have different identity/coverage. Hosted search is outside tool-hook coverage. A blocking post-tool hook can conceal the original result after side effects. Async completion does not start a turn. This supports narrow evidence-aware automation, not universal enforcement.
- [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24: the reported application experiment improved integration through evaluation, then removed costly scaffolding as model capability changed. Radical simplification did not preserve its result. Use this to compare measured additions and removals; it does not authorize removing the project's independent-review obligations or establish performance in another model or host.
- [Anthropic agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), 2026-01-09: realistic outcomes and transcript inspection complement automated scores; synthetic success can misrepresent real use. Use source-bound normal cases and counterexamples plus the actual next consumer, not only a static PASS suite.

Retain, narrow, merge or retire this route if actual uses show that its decision contribution fails to repay acquisition/maintenance cost. Keeping a well-supported method unchanged is a valid result; manufacturing a new idea is not.
