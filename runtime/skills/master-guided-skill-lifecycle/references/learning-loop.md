# Learning Loop: Next Use, Not Record Count

Use this route for a material result, meaningful reuse, recurring failure, avoidable cost, or decision-sensitive capability change. Keep ordinary read-only work proportionate. The current source and workflow govern; this reference cannot grant permissions or create a new deliverable.

## Consume Existing Knowledge Efficiently

Read current controls and search the applicable history in the project's chosen knowledge sources. `scripts/master_index.py build --master <global> --master <project> --cache <explicit-inactive-cache>` creates exact raw backing plus a heading and occurrence index without editing those sources. Reuse the index only while the bound source hashes remain current. Follow every `query --index <index> --term <term> [--controls] [--cursor <cursor>]` page before claiming complete query coverage. An empty query result does not prove that knowledge is inapplicable, and the index is neither semantic authority nor a merge decision.

The `master-history-v1` protocol follows exact immutable backing with path/hash checks and cycle detection. Normal queries reach current text and history; `--controls` selects only live-root control sections. A search of only the compact root is not complete history retrieval. Missing or stale backing holds only dependent knowledge use.

At a real organization trigger, `master_index.py propose-organization --help` describes a pure proposal for owner-selected historical sections. It returns complete old backing and a replacement current view, preserving all unselected bytes. The owner reviews the meaning and independent challenge, publishes backing first, applies the exact current replacement under a stale-writer check, and retains rollback. A proposal or index build performs no organization itself. Replace an affected family's current disposition; do not append competing current paragraphs or delete unresolved obligations by size, date or status guesses.

Keep each control scoped by its owner and objective. Do not replace the current product objective with a learning task. Preserve the complete relevant ID and disposition inventory and unresolved history; similar wording, paths, or identifiers do not prove semantic equivalence.

## Make the Next Improvement Action Explicit

From the actual project event, decide whether knowledge is confirmed, provisional, project-local, invalidated, or superseded. Include reusable successes and unnecessary procedures as well as failures. Prefer an existing invariant, a revision or merge, or removal of a harmful mechanism over duplicate guidance.

Use `scripts/learning_queue.py --help` for the exact command and schema. Its explicitly named per-project database stores candidate references and immutable transition history, not duplicate raw incidents. Bind the owner, objective and source, project event, reusable disposition, causal family, artifact, next consumer and trigger, evidence, and rollback appropriate to the current stage. Use revision comparison and idempotent event IDs; never overwrite an unknown effect with a retry. Unavailable metrics remain unavailable rather than becoming zero.

Correct stale reason, trigger or consumer references with `change_kind: metadata`, the same lifecycle state, current revision and reason reference. Preserve identity, prior evidence/source/rollback and immutable history. Ordinary same-state transitions remain invalid; do not manufacture advancement to fix a display.

The queue is a reminder and evidence-link validator, not action authority. Recording a candidate is not improvement. Carry out the next eligible preparation, evaluation, independent challenge, bounded activation, actual use, or effect assessment within current authority. An inactive candidate may be prepared while later activation evidence is still open; do not require a future successful effect before an otherwise authorized bounded trial.

Once standing source authority, preservation, representative normal-path evidence, independent challenge and rollback close, perform the eligible change without waiting for another user prompt. An exact user-condition amendment holds only its dependent change, not ordinary improvements that preserve those conditions.

If the current task would not recover the cost, retain a specific reason and next-use trigger and return at that event rather than on a timer. Retire only through an explicit disposition while preserving evidence and lineage. Optional learning work must not stall the primary objective.

## Verify Application and Effect

Keep materialized, registered, discoverable, selected, read, applied, and measured states distinct. Compare the actual changed action and consumer outcome with the predeclared baseline, including representative normal cases, misses, recurrence, induced rework, false holds, elapsed and integration cost, and maintenance cost. Component checks or a single use do not establish general benefit.

Instruction-only effects require a real action and result plus an independently identified observation. New permissions, materially uncertain semantics, or a changed trust definition require a user decision; source-preserving methods may improve through the existing gates. Update Skill and registry member hashes only after the reviewed candidate is frozen.

Report the decision-bearing learning: what changed, where it was next used, what was observed, and what remains unknown. Do not add a Skill quota, duplicate packet, mandatory extra agent, daemon, or automatic continuation.

When the impediment is an operating rule, follow [condition-stewardship.md](condition-stewardship.md). Use the same candidate and evidence references; do not create another queue or infer permission from queue status.
