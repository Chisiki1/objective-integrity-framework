# Stage Allocation View v1

`stage-allocation-v2` binds the decision to `objective_id`, `source_sha256`, `stage_id`, `job_id`, `job_shape_sha256`, `current_lease_id`, and `owner` (`lane`, `task_id`, `lease_id`). The result copies these identity fields before calculating `result_sha256`; a consumer must compare them to its current transition and recompute the allocator result rather than trusting a handwritten result file.

Run at a material job-shape change, not at a fixed interval. Candidate configuration IDs are opaque and must not encode a policy ranking. Admit only configurations whose job-derived capability needs are all evidenced. Compare observed risk-adjusted total cost that includes execution, waiting, tool, delegation, integration, re-verification, expected rework, and error harm. Costs are `observed`, `estimated` (nonnegative value plus evidence), `unavailable`, or source-selected. An estimated cost may be rationally compared without being promoted to observed. If a capable current configuration is tied or a competing cost is unavailable and measured context benefit is positive, retain it with `RETAIN_CURRENT`; genuine capability/authority ambiguity still returns `USER-DECISION`.

Preserve the current conversation when measured context/cache benefit is positive; this does not force one model or reasoning setting across stages. Representative eval version and the lower-configuration failure prediction remain part of the input evidence. Each candidate records model and reasoning as `selected / injectable / requested / accepted / effective / fallback`; effective fields stay null when the orchestrator does not expose them, and typed acceptance is not rewritten as an invented effective value. These are episode facts, never a normative model ranking. `stage-allocation-result-v2` adds `selection_basis`, per-candidate `cost_statuses`, and deterministic `result_sha256` over the result before that field. Output proves only typed admission and ordering, not model quality or future outcomes.
