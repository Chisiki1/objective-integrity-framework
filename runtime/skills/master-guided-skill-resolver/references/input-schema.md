# Fact compiler v2 and resolver input v1

## Material fact source v2

`scripts/compile_skill_facts.py` accepts `schema_version=mgskill-fact-source-v2` with:

- `objective_id`: non-empty source-bound objective identity.
- `source_claims`: exact non-empty source-clause ID array.
- `source_records`: exactly one record per source claim. Each record has exact `id`, `disposition` (`fact-bearing` or `no-selection-fact`), `evidence`, optional `reason`, and `facts`/`excluded_facts` objects using only the resolver fact fields.
- `action_records`: current job/action records with `id`, `disposition`, `evidence`, `finality` (`finalized` or `not-finalized`), `tool_schema.status` (`available`, `unavailable`, or `not-applicable`), and fact objects. Available schemas require an identity; unavailable schemas require a reason.
- `negative_selection_challenge`: `status=completed` plus a non-empty countermodel challenging omitted or concept-only facts.
- `blind_phase`: `none`, `initial`, or `reconciled`.

Allowed fact fields are `job`, `action`, `tool`, `environment`, `cause_families`, `permissions`, `resources`, `consumers`, and `risks`. Fact tokens are trimmed and case-folded; source IDs preserve exact case. Desired skill names are not input facts. Source text can constrain semantic applicability without becoming a registry trigger; current executable facts derive from the finalized action record.

The compiler rejects missing/duplicate clause dispositions, unknown fields, positive/excluded conflicts, fact-bearing records without facts, no-selection records with facts, and incomplete negative-selection challenge. It reports provenance, exclusions, exact/near/no-match candidates, finality/schema status, resolver input, and a compiler snapshot. `not-finalized` or unavailable schema is valid evidence with dependent action status `unproven`, not zero, PASS, or global No-Go.

The compiler proves typed provenance and registry-clause projection only. It cannot prove semantic completeness, applicability, objective fidelity, tool execution, or skill benefit.

## Builder plan v1

`build_skill_fact_input.py` accepts `mgskill-fact-builder-plan-v1`, an exact source-document path, source-claim IDs and one disposition record per ID, then emits the v2 input. It derives the source document hash, exact clause text hashes and canonical final-payload hashes. Supply the current registry only to reject desired skill IDs/names used as facts; the builder never selects an entry. A malformed plan is rejected before the compiler runs.

The complete builder plan carries the actual `current_authority.message`; `source_document.path`; `objective_id`; `source_claims`; `blind_phase`; a record for every claim containing its actual authoritative `text` (generated by the builder), `classification`, `intent`, `mechanism`, `disposition`, evidence, facts/exclusions; every action `id`, finality, facts/exclusions, complete `final_payload`, canonical `final_payload_sha256` (generated), and full `tool_schema`; and a completed negative-selection challenge. Do not hand-write an output source record or payload hash.

```json
{"schema_version":"mgskill-fact-builder-plan-v1","objective_id":"OBJ","current_authority":{"message":"exact authority"},"source_document":{"path":"C:/exact/source.json"},"source_claims":["SRC-1"],"blind_phase":"none","source_records":[{"id":"SRC-1","disposition":"fact-bearing","classification":"method","intent":"why","mechanism":"how","evidence":"exact source","facts":{"job":["bounded-job"]},"excluded_facts":{}}],"action_records":[{"id":"ACT-1","disposition":"fact-bearing","evidence":"final action","facts":{"job":["bounded-job"]},"excluded_facts":{},"finality":"finalized","final_payload":{"facts":{"job":["bounded-job"]}},"tool_schema":{"status":"not-applicable"}}],"negative_selection_challenge":{"status":"completed","countermodel":"omitted fact is not a selector"}}
```

## Resolver input v1

The compiler emits `mgskill-resolve-input-v1` with `objective_id`, `source_claims`, all nine normalized fact arrays, and `blind_phase`. `now_utc` is optional. Registry clauses use exact token equality, not fuzzy similarity or first-match priority; every field named by a clause must match at least one corresponding token.

Legacy manually assembled v1 inputs remain mechanically readable, but they cannot close the material v2 provenance/finality/negative-selection claim.
